# Захист основної гілки: аудит та умови приймання

**Завдання:** [УКР-07 / Issue #8](https://github.com/juv4uk/ukrainian-books/issues/8).  
**Статус:** технічний аудит; це **не ввімкнення адміністративного захисту**.  
**Дата початкової перевірки:** 31 жовтня 2026 року.

## Фактичний стан

У публічній відповіді [GitHub branch API](https://api.github.com/repos/juv4uk/ukrainian-books/branches/main)
поле protected було **false**, а [API rulesets](https://api.github.com/repos/juv4uk/ukrainian-books/rulesets)
повертав порожній список. Підключення GitHub у цій сесії не має адміністративного
інструмента для зміни цих параметрів.

**Увага:** значення protected=true саме по собі не доводить, що налаштовано
незалежний review, необхідні status checks, заборону force-push і видалення.
Потрібен окремий огляд реальних правил у GitHub.

## Команди

З кореня репозиторію:

~~~sh
python3 -m unittest discover -s tests -p 'test_audit_main_protection.py' -v
python3 scripts/audit_main_protection.py --repo juv4uk/ukrainian-books
python3 scripts/audit_main_protection.py --repo juv4uk/ukrainian-books --require-protected
python3 scripts/check_project.py
~~~

Перший виклик перевіряє логіку без мережі. Другий створює JSON у
reports/branch-protection.json у **інформаційному режимі** та завершується
успішно навіть за незахищеної гілки. Третій — **строгий режим**: код виходу 2
якщо GitHub не підтвердив protected=true (включно з HTTP 403 і невідомим
станом). Навіть успішний строгий режим не перевіряє правила рецензування.

Необов'язкова змінна середовища GITHUB_TOKEN потрібна лише для
автентифікованого читання API; токен ніколи не має потрапляти у звіт.
[Workflow аудитора](../.github/workflows/audit-main-protection.yml)
запускає офлайнові тести й інформаційну перевірку, публікує JSON як артефакт.
Його зелений CI **не означає захищений main**.

## Що має зробити власник репозиторію

У GitHub відкрийте **Settings → Rules → Rulesets → New branch ruleset**,
виберіть цільову гілку **main**, встановіть **Active** і перевірте:

1. Вимагати PR перед злиттям; заборонити пряме внесення змін до main.
2. Вимагати принаймні **одне незалежне схвалення** та, за можливості,
   відкидати застарілі схвалення після оновлення комітів. Самооцінювання
   агента не прирівнюється до незалежної рецензії.
3. Увімкнути **Required status checks**: точні назви job/status context
   треба взяти з вкладки Checks останнього PR. Обов'язковими мають бути
   перевірки структури й ліцензії; перевірки походження та реєстру
   віршів — за актуальною політикою видання. Не вгадувати назви job
   лише з назв workflow.
4. Заборонити **force-push** та **видалення main**. Не створювати bypass
   для автономних агентів; за можливості вимагати розв'язані обговорення
   та актуальну гілку перед злиттям.
5. Перевірити фактичну доступність потрібних правил на плані GitHub.

## Доказовий контроль після налаштування

- Повторно прочитати GitHub branch API та перелік дієвих правил у Settings.
- На тестовому PR без схвалення перевірити, що Merge заблокований.
- Після нового коміту перевірити дію політики застарілих схвалень,
  якщо її налаштовано.
- Перевіряти заборону force-push на **окремій тестовій гілці**
  з аналогічним ruleset, не ризикувати справжньою main.
- Зафіксувати у [Issue #8](https://github.com/juv4uk/ukrainian-books/issues/8)
  відповідального, дату, URL набору правил, точні перевірки та результати.
