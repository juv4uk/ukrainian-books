# Звіт про чергу рецензування PR

**Статус:** технічний інструмент спостереження. Не є філологічною, редакторською, правовою рецензією чи дозволом на злиття. Пов'язане завдання: [РЕД-03 / #109](https://github.com/juv4uk/ukrainian-books/issues/109).

## Для чого

Черга містить багато чернеткових PR. Щоб визначити, кого запросити до незалежного перегляду, скрипт читає **тільки** відкриті PR, GitHub Reviews та GitHub check-runs, прив'язані до поточного head SHA. Він показує спостережені ознаки, але **ніколи не робить merge, не змінює міток, статусів, текстів чи налаштувань**.

## Запуск

```sh
python3 -m unittest discover -s tests -p 'test_review_queue.py' -v
GITHUB_TOKEN=... python3 scripts/report_review_queue.py --repo juv4uk/ukrainian-books
```

Токен потрібний для надійнішого доступу до GitHub API (лише читання: PR та checks). Його не друкують і не записують у файли. Якщо немає токена, скрипт може виконати анонімний запит у межах публічного ліміту. Для відтворюваних офлайн-перевірок: `python3 scripts/report_review_queue.py --fixture шлях/до/вашого-набору.json`, де JSON — список об'єктів з ключами `pr`, `reviews`, `checks` у відповідних форматах API GitHub. Не зберігайте персональні дані, токени чи сторонні тексти у фікстурах.

Ручний workflow **«Черга рецензування — спостережний звіт»** запускає всі unit-тести й після них формує поточний JSON-звіт у журналі Actions. На PR/push виконує лише офлайн-тести: зміни іншого учасника не повинні діставати токен для зовнішніх запитів. Звіт не публікує коментарів до PR і не створює автоматичних рецензій.

## Як читати результати

- `draft` — автор ще не вивів PR із чернетки.
- `approvals_current_sha` — останні **неавторські** схвалення саме поточної ревізії; самосхвалення і схвалення старого SHA не враховуються.
- `approvals_stale_sha` — останнє схвалення від рецензента стосується старого SHA. Воно не є доказом перегляду актуального тексту.
- `changes_requested` — останній стан рецензента містить вимогу змін.
- `checks_unverified` — незавершені, пропущені, нейтральні або невдалі перевірки. `checks_observed=0` **не означає успішний CI**: деякі Actions звітуються на тимчасовому merge SHA, а не на head SHA.
- `manual_requirements` — правове погодження походження, незалежне філологічне/редакторське рецензування й остаточна перевірка захисту `main` **завжди потрібні**.
- `automatically_mergeable` — **завжди `false`**. Навіть усі `success` не підтверджують, що було запущено саме обов'язкові checks, чи дозволено передрук цифрової транскрипції.

Порядок: автор доводить текст до стану, придатного для перегляду → незалежний рецензент читає джерела GRETIL/SARIT та українську редакцію й фіксує review → аудитор прав підтверджує підставу публікації власного та цитованого матеріалу → координатор перевіряє актуальні SHA, обов'язкові checks, конфлікти та умови захисту гілки. **Цей звіт не замінює жоден з цих кроків.**

## Межі даних

Звіт є миттєвим зрізом. Він не знає прав на твір, повноти історичних видань, незалежності реального рецензента поза його GitHub-логіном, валідності наукового аналізу та налаштувань branch protection. API-помилка призводить до ненульового коду виходу й **не маскується** порожньою чергою. GitHub повертає reviews у хронологічному порядку; береться останнє **рішеннєве** review кожного рецензента (`APPROVED`, `CHANGES_REQUESTED` або `DISMISSED`). Пізніші `COMMENTED` і `PENDING` не скасовують схвалення чи запит змін; `DISMISSED` скасовує. Це консервативна модель для звіту, а не повна реконструкція правил GitHub branch protection. Понад 100 check-runs на одному head SHA спричиняють явну помилку, а не хибно повний звіт.
