### 1.1. Чого саме досягає CODEOWNERS

`.github/CODEOWNERS` — це декларація. GitHub використовує її, щоб **автоматично
призначати рецензентів** і показувати їх у PR. Правило стає **блокувальним** лише
після того, як у branch protection увімкнено «Require review from Code Owners»
(крок 2.4 нижче). Без цього кроку CODEOWNERS не заважає злити PR без рецензії.

Власник у файлі один — `@juv4uk`. Це не спрощення, а факт: станом на 31.10.2026
це єдиний колаборант репозиторію з правами `admin` і автор усіх комітів у `main`.
Коли з'явиться другий рецензент, достатньо замінити `@juv4uk` у потрібних рядках.

workflow і не зі здогадів. У списку вибору в Settings GitHub може показувати їх у формі
`<назва workflow> / <назва job>`, тому в таблиці наведено обидві форми; сама перевірка
при цьому називається дослівно так, як у стовпчику «назва перевірки» (див. 2.4).

### 2.1. Мінімальний набір, який треба внести в «Require status checks to pass»

Скопіюйте рівно ці п'ять назв:

```
Структура, права та посилання
Мінімальні права й безпечні тригери
Перевірка паспортів і негативні тести
Нумерація, цілісність та дефект 18.95
Схема карток і синтетичні тести
```

За бажанням додайте шосту: `Тести аудитора та інформаційний звіт`.

### 2.2. Чому `pdf-smoke.yml` не можна робити обов'язковим

`pdf-smoke.yml` запускається лише тоді, коли змінено `tests/fixtures/pdf-smoke-ukr.tex.in`
або сам файл workflow. Якщо назву зробити обов'язковою, на PR без цих шляхів перевірка
не запуститься, лишиться в стані «Expected» і **назавжди заблокує злиття**. Тримайте
її необов'язковою.

### 2.3. Чому `build-books.yml` не може бути обов'язковим

Його єдиний тригер — `workflow_dispatch`, тобто ручний запуск. На PR він не
з'являється взагалі, тому вибрати його в списку обов'язкових перевірок не вийде.

### 2.4. Перевірено на практиці

Назви в третьому стовпчику — не припущення. Після відкриття PR #168 GitHub повернув
саме шість перевірок із такими назвами, дослівно, без префікса назви workflow:

```
Тести аудитора та інформаційний звіт          success
Нумерація, цілісність та дефект 18.95         success
Схема карток і синтетичні тести               success
Перевірка паспортів і негативні тести         success
Мінімальні права й безпечні тригери           success
Структура, права та посилання                 success
```

У списку вибору в Settings GitHub може показувати їх із префіксом назви workflow
(`Якість і походження / Структура, права та посилання`) — орієнтуйтеся на частину
після скісної риски, вона мусить збігатися дослівно, разом із регістром, пробілами
й розділовими знаками (зокрема «18.95» з точкою).

### 2.5. Якщо назви в списку Settings не збігаються

Список перевірок у Settings наповнюється лише тими перевірками, які **вже хоч раз
запускалися** в репозиторії. Якщо потрібної назви немає — відкрийте будь-який PR,
дочекайтеся завершення потрібного workflow і повторіть налаштування. Не вписуйте
назву вручну «на око»: одрук у назві створює перевірку, яка ніколи не з'явиться,
і блокує злиття назавжди.

## 3. Налаштування, які треба зробити в Settings (покроково)

Виконує **власник репозиторію** (`@juv4uk`) — потрібні права `admin`. Агент, який
підготував цей документ, таких прав не має і **нічого з переліченого не вмикав**.

### 3.1. Створити правило

1. Відкрийте `https://github.com/juv4uk/ukrainian-books/settings/branches`.
2. **Branch protection rules** → **Add branch protection rule** (або **Add classic
   branch protection rule**).
3. **Branch name pattern:** `main` — рівно `main`, без `*`, без пробілів.
4. Далі — пункти 3.2–3.9, після чого **Create** / **Save changes**.

> Альтернатива для тих, хто вже працює з rulesets: `Settings → Rules → Rulesets →
> New branch ruleset`, **Target branches** → `main`, **Enforcement status: Active**
> (не `Evaluate` — у режимі Evaluate правила лише пишуть попередження і нічого не
> блокують). Назви налаштувань там інші, а зміст той самий; нижче наведено класичний
> варіант, бо він має всі потрібні пункти з точними назвами.

### 3.2. Require a pull request before merging

- [ ] **Require a pull request before merging** — увімкнути.
- [ ] **Require approvals** — `1`.
- [ ] **Dismiss stale pull request approvals when new commits are pushed** — увімкнути.
- [ ] **Require review from Code Owners** — увімкнути (це те, що робить `.github/CODEOWNERS` блокувальним).
- [ ] **Require approval of the most recent reviewable push** — увімкнути, якщо доступно.
- [ ] **Require conversation resolution before merging** — увімкнути.

### 3.3. Require status checks to pass before merging

- [ ] **Require status checks to pass before merging** — увімкнути.
- [ ] **Require branches to be up to date before merging** — увімкнути.
- [ ] У полі пошуку додати п'ять назв із розділу 2.1 (кожну окремо, зі списку, не вручну).

### 3.4. Require linear history

- [ ] **Require linear history** — увімкнути (забороняє merge-коміти, історія `main` лишається читабельною).

### 3.5. Заборона обходу

- [ ] **Do not allow bypassing the above settings** — увімкнути.
- [ ] Переконайтеся, що пункт поширюється і на адміністраторів (у класичному
      інтерфейсі це те саме поле; у rulesets — **Bypass list** має лишитися порожнім).

### 3.6. Restrict who can push

- [ ] **Restrict who can push to matching branches** — увімкнути.
- [ ] У списку дозволених лишити тільки `@juv4uk` (або порожній список — тоді прямі
      push заборонені всім, включно з власником, і всі зміни йдуть через PR).

> Наслідок, який треба усвідомити: у поєднанні з 3.5 це означає, що **навіть власник
> більше не зможе запушити напряму в `main`**. Це саме те, чого домагається задача, але
> це незворотна зміна робочого процесу — робіть її свідомо.

### 3.7. Allow force pushes

- [ ] **Allow force pushes** — **вимкнено** (не позначено). Жодних винятків для
      користувачів чи команд.

### 3.8. Allow deletions

- [ ] **Allow deletions** — **вимкнено** (не позначено).

### 3.9. Необов'язково, але доречно

- [ ] **Require signed commits** — увімкнути, якщо всі учасники мають налаштований GPG/SSH-підпис.
- [ ] **Lock branch** — **не вмикати**: це режим «тільки читання», він зупинить будь-яку роботу.

### 3.10. Проблема, яку треба вирішити перед увімкненням «Require approvals: 1»

Станом на 31.10.2026 у репозиторії **один** колаборант — `@juv4uk` з правами `admin`.
GitHub не зараховує автору PR його власне схвалення. Отже, якщо увімкнути
«Require approvals: 1» разом із «Do not allow bypassing» і «Restrict who can push»,
**жоден PR не можна буде злити**, доки не з'явиться другий рецензент із правом запису.

Два виходи, вибір — за власником:

- **A (рекомендовано):** запросити другого рецензента з правом `write`
  (`Settings → Collaborators and teams → Add people`) і лишити `Require approvals: 1`.
  Це єдиний варіант, за якого «обов'язкове рецензування PR» справді виконується.
- **B (тимчасово):** `Require approvals: 0`, але з увімкненими рештою пунктів
  (PR, обов'язкові перевірки, заборона force-push і видалення). Захист від випадкових
  змін працює, але вимога незалежної рецензії — ні. Таке рішення треба зафіксувати
  в [Issue #8](https://github.com/juv4uk/ukrainian-books/issues/8) із датою й причиною.

**Стан змінюється швидше, ніж документ.** У першій перевірці того самого дня
(31.10.2026) Issues #2, #3 і #6 були **закриті**, а за годину з невеликим — уже
відкриті: їх перевідкрили. Це не помилка знімка, а властивість репозиторію з багатьма
паралельними учасниками: будь-який статичний перелік станів застаріває негайно. Тому
єдине джерело істини — відкриті Issues на GitHub, а `tasks/ISSUES.json` — історичний
знімок плану.

### 5.1. Зафіксовані розбіжності

1. **Немає номера Issue.** Реєстр не пов'язує код `УКР-0N` із номером Issue. Зв'язок
   зараз відновлюється лише за дослівним збігом заголовка — це крихко: будь-яка
   правка заголовка в GitHub розриває відповідність.
2. **Немає стану.** У реєстрі немає поля `state`, тому він не відрізняє закриту роботу
   від відкритої. Наскільки це практично: того ж дня Issues #2, #3 і #6 були закриті,
   а потім перевідкриті — реєстр не помітив ні першого, ні другого. Хто читає лише
   `tasks/ISSUES.json`, дістане хибне уявлення про обсяг відкритої роботи.
3. **Коди поза реєстром.** На GitHub є `УКР-09` (Issue #21 відкрито, #22 закрито;
   PR #27 і #29 закрито) і `УКР-11` (PR #141 закрито, PR #157 відкрито). У
   `tasks/ISSUES.json` їх немає.
4. **Пропущений код.** `УКР-10` відсутній і в реєстрі, і серед Issues — або його
   справді не було, або він існував під іншим номером. З наявних даних це не
   встановлюється; у документі це позначено як невідоме, а не вигадане.
5. **`scripts/bootstrap_issues.py` не оновлює, а лише створює.** Він порівнює
   заголовки й створює відсутні Issues; наявні не оновлює і станів не змінює.
   Повторний запуск безпечний для цих 8 заголовків (усі вже є), але додавання нового
   запису в реєстр без номера Issue призведе до створення дубля, якщо Issue вже існує
   з іншим заголовком.

### 5.2. Чому `tasks/ISSUES.json` не переписано

Це може бути чужа робота: реєстр створено до появи `УКР-09` і `УКР-11`, і його зміна
в межах PR про захист `main` змішала б дві різні задачі (порушення правила 3 з
`CONTRIBUTING.md`). Розбіжності зафіксовано тут; приведення реєстру до реальності —
окрема робота з окремим Issue і CLAIM.

### 5.3. Запропонований порядок керування Issues (без зміни файлів)

1. Issue створюється з шаблону `research.yml` або `translation.yml` (або порожнім —
   це дозволено `config.yml`).
2. До початку редагування в Issue пишеться **CLAIM**: виконавець, файли, дата, межі.
3. Кожен код `УКР-NN`, `АҐ-…`, `РЕД-…`, `КООРД-…` має рівно одну Issue-власника; PR
   посилається на неї.
4. Issue закривається лише після злиття PR, зелених перевірок і рецензії.
5. `tasks/ISSUES.json` — знімок початкового плану, не джерело істини. Джерело істини —
   відкриті Issues на GitHub.

## 6. Чого файли зробити не можуть — і чому

Це найважливіший розділ. Кожен пункт — це не «не встигли», а структурна межа між
git-репозиторієм і сервером GitHub.

1. **Увімкнути branch protection.** Правила захисту гілки зберігаються в базі GitHub,
   а не в репозиторії. Жоден файл у git не може створити правило, бо ніде немає місця,
   куди його записати: API `PUT .../branches/main/protection` — це окремий
   адміністративний виклик, який потребує прав `admin` і токена з відповідним scope.
   Сесія, у якій готувався цей документ, таких прав не має; спроба прочитати
   налаштування повернула «правил не налаштовано», а не «немає доступу».
2. **Зробити перевірку обов'язковою.** Список required status checks — це поле
   серверного правила. У YAML workflow немає і не може бути поля на кшталт
   `required: true`: workflow лише *повідомляє* результат, а *вимагати* його може
   тільки branch protection.
3. **Заборонити force-push і видалення гілки.** `.gitattributes`, хуки в репозиторії
   та `pre-push`-хуки діють лише на машині того, хто їх має; вони не заважають
   `git push --force` з іншого клієнта і не захищають від `DELETE` гілки через API.
4. **Зробити CODEOWNERS блокувальним.** Файл лише призначає рецензентів. Поки не
   увімкнено «Require review from Code Owners», PR із нерецензованими змінами в
   `scripts/` чи `.github/workflows/` зіллється без перешкод.
5. **Обмежити права людей.** `permissions:` у workflow обмежує `GITHUB_TOKEN` під час
   виконання job-а. Це не має жодного стосунку до того, хто з людей може пушити в
   `main`: це визначають роль колаборанта і пункт «Restrict who can push».
6. **Заборонити адміністратору обходити правила.** За замовчуванням адміністратор
   репозиторію може знехтувати branch protection. Це змінюється лише пунктом
   «Do not allow bypassing the above settings» у Settings.
7. **Гарантувати рецензію.** Рецензія — дія людини. Поки в репозиторії один
   колаборант, «обов'язкове рецензування» або блокує всі PR, або не виконується
   взагалі (розділ 3.10). Жоден файл цього не розв'язує.
8. **Довести, що захист працює.** Зелений CI означає лише «перевірки пройшли». Він не
   є доказом наявності правил. Тому `scripts/audit_main_protection.py` і workflow
   `audit-main-protection.yml` навмисно пишуть у звіт `"рев'ю_підтверджено": false`,
   `"обов'язкові_CI_підтверджено": false`, `"заборону_force_push_підтверджено": false`
   і прямо застерігають, що поле `protected` саме по собі нічого не доводить.

Детальніший технічний аудит — у `MAIN_PROTECTION.md`, стисла версія кроків —
у `MAIN_PROTECTION_CHECKLIST.md`.

## 7. Як перевірити стан після налаштування

1. Відкрити `https://github.com/juv4uk/ukrainian-books/settings/branches` і переконатися,
   що правило для `main` існує і що в ньому позначені пункти 3.2–3.8.
2. Запустити аудит:

```sh
python3 scripts/audit_main_protection.py --repo juv4uk/ukrainian-books
python3 scripts/audit_main_protection.py --repo juv4uk/ukrainian-books --require-protected
```

Другий виклик повертає код 2, якщо GitHub не підтвердив `protected: true`. Успіх цієї
команди **все одно не доводить** наявності рецензування й обов'язкових перевірок —
лише те, що гілка позначена захищеною.

3. Практична перевірка на тестовому PR: відкрити PR без схвалення і переконатися, що
   кнопка **Merge** заблокована з повідомленням про потрібну рецензію.
4. Практична перевірка застарілих схвалень: після схвалення додати новий коміт і
   переконатися, що схвалення зникло.
5. Перевірку заборони force-push робити на **окремій тестовій гілці** з таким самим
   правилом, а не на справжній `main`.
6. Записати в [Issue #8](https://github.com/juv4uk/ukrainian-books/issues/8):
   хто налаштував, дату, перелік увімкнених пунктів, назви обов'язкових перевірок,
   кількість потрібних схвалень і результат кроків 3–4.

Лише після цього `main` можна називати захищеним. До того — **не можна**.
