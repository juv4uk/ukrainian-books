# Контроль перетину файлів між відкритими PR

Пов'язано з [КООРД-01](https://github.com/juv4uk/ukrainian-books/issues/104). Це **координаційний інструмент**, не текстологічний чи юридичний висновок.

## Проблема і правило

31.10.2026 кілька незалежних PR одночасно додавали `editorial/cards/2.5.json` (PR #53, #56, #58) і `editorial/cards/4.1.json` (PR #80, #83). Однакові шляхи у **різних гілках** не видно перевірці дублів у дереві `main`.

Новий [workflow](../.github/workflows/pr-overlap.yml) на `pull_request` порівнює **точні імена змінених файлів** поточного PR з ранішими **відкритими** PR (менший номер). Якщо спільний шлях знайдено, новіший PR отримує помилку з номерами раніших PR та шляхами. Для перейменувань ураховуються **обидва** поля відповіді GitHub: `filename` (нова назва) і `previous_filename` (стара назва); відсутня або некоректна стара назва за `status: renamed` спричиняє помилку перевірки. Перший PR і незв'язані зміни не блокуються. Закриття старішого PR прибирає перетин на **новому запуску** перевірки; результати попередніх запусків не змінюються самі.

## Як читаються дані

Перелік відкритих PR і їхні змінені файли беруться **пакетним GraphQL-запитом**: один запит на кожні 100 відкритих PR. На 107 відкритих PR це 2 GraphQL-запити плюс точковий REST за потреби — у вимірюванні 31.10.2026 разом **3 запити** замість 109 (перелік + по одному `/pulls/{n}/files` на кожен раніший PR). REST залишається лише точковим уточненням для трьох випадків, де GraphQL неповний: перейменування (у GraphQL немає `previous_filename`), понад 100 змінених файлів у PR і незавершена пагінація файлів.

Кількість запитів до API не впливає на строгість: будь-яка неповнота — `errors` у відповіді, менше файлів, ніж оголошено, розбіжність `changedFiles` і `files.totalCount`, коротший за оголошену кількість перелік PR — це **помилка перевірки**, а не зелений результат.

## Діагностика збоїв

При збої API друкується тип винятку, HTTP-статус, URL, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, `Retry-After` і перші 200 символів тіла відповіді. Токен не друкується ні повністю, ні частково: заголовки запиту не виводяться ніколи, а тіло й адреса додатково проходять редагування — навіть якщо сервер відлунить отриманий `Bearer` назад у тексті.

Три стани розрізняються навмисно:

- **429, або 403 з ознаками ліміту** — стан інфраструктури GitHub, не дефект PR. Перевірка спершу чекає (з повагою до `Retry-After` і `X-RateLimit-Reset`), а якщо ліміт не минув — голосно друкує «ПРОПУЩЕНО» з причиною, `::warning::` і `"status": "skipped"`, код 0.
- **401, або 403 без ознак ліміту** — дефект конфігурації: токен недійсний або без прав. Червоне з названою причиною, код 2.
- **мережа, таймаут, 5xx** — не провина PR: «ПРОПУЩЕНО» з причиною, код 0.

Пропуск — це **не** зелений результат: у JSON видно `"status": "skipped"` і причину, тож «перетинів немає» ніколи не вигадується. Послаблено лише реакцію на інфраструктуру, не на сам гейт: невалідний JSON, `errors`, часткові дані, відсутній PR і перетин шляхів лишаються червоними.

Менший номер — **лише детермінований пріоритет попередження**, не дозвіл на редагування і не автоматичне визнання CLAIM. Якщо старіший PR не має належного CLAIM або роботу вже передано, координатор з'ясовує ситуацію та документує рішення; обходити контроль шляхом вимкнення workflow не можна.

## Перевірки

```sh
python3 -m unittest discover -s tests -p 'test_check_pr_overlaps.py' -v
python3 scripts/check_project.py
```

Для живого аудиту потрібні GitHub API й токен **лише з read-доступом**:

```sh
python3 scripts/check_pr_overlaps.py --repo juv4uk/ukrainian-books --pr 83 --strict
```

Токен передавайте через змінну середовища `GITHUB_TOKEN`, не записуйте його в команди, логи чи файли, що потрапляють у Git. У GitHub Actions токен передається через `github.token` з `contents: read`, `pull-requests: read`, без `pull_request_target`, без write і без коментарів від імені бота. Помилка API, відсутній токен, невалідний JSON чи неповна відповідь завершуються **кодом 2**, не фальшивим успіхом. Код 1 — реальний збіг, 0 — перетинів немає **або** перевірку пропущено з названою інфраструктурною причиною (`"status": "skipped"`).

Для офлайнових випадків доступний `--snapshot шлях.json`, структура `{"pulls": [{"number": 53, "files": ["editorial/cards/2.5.json"]}]}`; це **синтетичний тест**, не перевірка поточного GitHub.

## Обмеження

- Перевіряються лише **ідентичні шляхи**, не однаковий вірш у двох різних файлах чи Markdown-діапазонах; для цього потрібні CLAIM та редакторська процедура.
- Уже відкриті PR проходять цей контроль тільки після нового `synchronize` / `reopened` / `ready_for_review` чи окремого запуску, якщо його налаштовано; немає постійного нагляду за змінами інших PR.
- GitHub API повертає до 3000 змінених файлів на один PR; досягнення межі — **помилка**, а не зелений результат.
- GraphQL віддає по 100 вузлів на сторінку: за понад 100 відкритих PR аудит робить кілька запитів. Якщо між сторінками PR відкриють або закриють, зібраний перелік може виявитися коротшим за оголошену кількість — це **помилка**, а не тихий пропуск.
- Без налаштованих адміністратором [branch rulesets](MAIN_PROTECTION.md) зелений workflow не є обов'язковою умовою злиття. Захист `main` має забезпечити власник репозиторію.
- Навіть успішні CI і відсутність перетину не є **незалежною академічною рецензією**, погодженням прав чи дозволом на злиття чернеток.

Жодних змін до «ВОЛЬНОСТІ» або сторонніх текстів цей інструмент не робить.
